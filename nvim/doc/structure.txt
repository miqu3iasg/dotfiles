NAME
    structure - the folder structure of this Neovim configuration

SYNOPSIS
    doc/structure.txt                       this page
    doc/reading.txt                         how to read the pages

DESCRIPTION
    The tree is organized so that every kind of knowledge has exactly one home: editor behavior at startup, plugin
    adapters, whole features, shared helpers, language servers, snippets and filetype options each get a folder of their
    own. A new contributor should be able to guess where a change goes from the change alone, without reading the
    code first.

THE TREE
    nvim/
    |- init.lua               entry point; fixes the load order, nothing else
    |- colors/                custom colorschemes, one file per scheme
    |- after/
    |  |- ftplugin/           buffer-local options per filetype, applied
    |  |                      after the runtime ftplugins
    |  |- queries/            Tree-sitter query overrides
    |- lua/
    |  |- config/             editor behavior loaded at startup
    |  |- plugins/            one adapter file per plugin suite
    |  |- modules/            whole features written for this config
    |  |- lib/                shared utilities and domain logic
    |  |- language/           the language server stack
    |  |- snippets/           LuaSnip snippets, one file per filetype
    |  |- archived/           deprecated modules, off the runtimepath
    |- pandoc/                Pandoc pipeline: defaults, metadata, profiles
    |                         and Lua filters
    |- resources/             example configuration for external tools
    |- spell/                 custom spell files
    |- doc/                   the doc pages, plain text (this folder)
    |- nvim-pack-lock.json    revision lock file written by vim.pack
    |- LICENSE

TOP-LEVEL FOLDERS
    colors/
        Colorschemes are runtimepath-loaded by `vim.cmd.colorscheme`, so they live in the conventional colors/ folder,
        outside lua/. One file per scheme; the scheme name is the file name.

    after/
        The after/ directory is loaded after everything else in the runtimepath, which is exactly what filetype
        overrides need: after/ftplugin/<ft>.lua runs after Neovim's own ftplugin for the filetype, so its options win.
        That is why every filetype option lives here and not in a custom layer. after/queries/ overrides Tree-sitter
        queries the same way (Markdown textobjects).

    pandoc/
        The export pipeline is data, not code: defaults.yaml (the writer pipeline), metadata.yaml (default layout and
        language), profiles/ (per-document styles, such as abnt.yaml) and filters/ (wikilinks, metadata blocks,
        citations). The Lua module lua/modules/pandoc.lua orchestrates these files; it holds no document logic itself.

    resources/
        Example configuration files for external tools that the config does not own (clang-format.example.yaml). Kept
        out of lua/ because they are reference material, never loaded.

    doc/
        The doc pages describing the config, plain text in the style of a man page, written at full width for the
        editor to wrap. doc/reading.txt explains how to read them; the standard itself is documentation.txt.

    spell/
        Custom spell dictionaries, loaded by Neovim's spelling machinery directly.

THE LUA LAYERS
    Everything under lua/ is split into layers by what a file is, and the split is the contract:

    config/ - behavior loaded at startup
        options.lua (global options), autocmds.lua (global autocmds), commands.lua (user commands), pack.lua (vim.pack
        declarations and build hooks), and keymaps/ (keymaps split by theme, one file per group, with its own init.lua
        that sets the leaders). Files here run once, in the order fixed by init.lua, and are not required by
        anything else.

    plugins/ - adapters for third-party plugins
        One file per plugin suite, never more. The file owns the plugin's setup and any keymap that only makes sense
        inside it. A plugin that should load lazily declares that itself, at the bottom of its own file, through
        lib/lazy.lua. init.lua in this folder is the ordered load list.

    modules/ - whole features written for this config
        Self-contained components such as the statusline, per-directory sessions, the scratch buffer, the compile runner
        and the notes workflow. Each exposes setup() when it must register commands, autocmds or keymaps, and owns its
        own state, reached only through its API. See doc/modules.txt.

    lib/ - shared utilities and domain logic
        Everything that exists to be required by other modules: the buffer helpers, the big-file detector, the lazy
        loader, the autoformat state, the export path logic and so on. The criterion is binary: something that exposes
        commands, autocmds or keymaps goes in modules/; anything else goes in lib/. See doc/lib.txt.

    language/ - the language server stack
        One module per server under servers/ (config table plus an optional on_attach hook), the shared setup in
        init.lua, the module contract in types.lua and the external linters in lint.lua. It slots into the plugins load
        list as a full module, because it must load between completions and fzf.

    snippets/ - LuaSnip snippets
        One file per filetype, loaded lazily; shared and filetype-adaptive helpers in common.lua.

    archived/ - deprecated, not deleted
        Modules kept around for possible future use. They sit outside lua/ and off the runtimepath on purpose: Neovim
        cannot reach them, but git history and the headers stay intact.

LAYER RULES
    A layer may only require the layers below it, in this order:

        init.lua > config > plugins > modules > lib

    Nothing in lib/ requires upwards, ever. This is what makes removal cheap: deleting an eager plugin means deleting
    its file in plugins/, its entry in config/pack.lua and its entry in plugins/init.lua; a lazy plugin is fully
    self-declared in its adapter and vanishes with that file alone.

    The rule also decides disputes. When a change wants to break it - a lib helper that wants to create a command, a
    module that wants to be required by lib - the fix is structural, not a workaround: move the domain logic to lib/ and
    let the caller pass state in, or merge the two files into the lower layer.

FINDING THINGS
    Where does X live?

        An option                 config/options.lua, or after/ftplugin/<ft>.lua when per filetype
        A global autocmd          config/autocmds.lua
        A user command            config/commands.lua, or the module that owns it
        A keymap                  the matching file in config/keymaps/, or the plugin's adapter when plugin-specific
        A plugin's setup          its adapter in plugins/
        A whole feature           the module in modules/ named after it
        A helper other files use  lib/
        A language server         language/servers/<server>.lua
        An external linter        language/lint.lua
        A snippet                 snippets/<ft>.lua
        Filetype options          after/ftplugin/<ft>.lua
        Export path logic         lib/exports.lua
