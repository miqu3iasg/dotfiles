.TH DOCUMENTATION 7 "2026" "nvim config"
.SH NAME
documentation \- the documentation standard of this Neovim config
.SH SYNOPSIS
.nf
man \-l doc/pages/documentation.txt
:read !man \-l doc/pages/documentation.txt
.fi
.SH DESCRIPTION
.PP
Documentation in this config is an engineering artifact, not
decoration. It exists so that a future reader \- usually the author,
six months later \- can understand a module's purpose, its decisions
and its external requirements without opening a single other file.
.PP
Three principles govern it:
.IP \(bu 2
The code is the primary documentation. Comments explain why, not
what; the what is the code itself.
.IP \(bu 2
Every file is self-contained. A reader of a file should not need to
open others to know what it does; instead of narrating elsewhere,
cross-reference with \fBSee:\fR.
.IP \(bu 2
Documentation lives next to the thing it documents. There is no
parallel manual to keep in sync; the headers of the files are the
manual, and the pages in \fIdoc/\fR are only overviews of it.
.SH THE LAYERS
.PP
Documentation exists in three layers, from nearest to farthest:
.TP
.B Header comments
every file under \fIlua/\fR and \fIafter/ftplugin/\fR opens with a
comment block describing itself. This is the primary and most
detailed layer.
.TP
.B doc/ man pages
overviews for a reader new to the config: what exists, where it
lives, how the pieces relate. Never a substitute for the headers.
Formatted as man pages (see
.B MAN PAGES IN doc/
below).
.TP
.B README.md
the repo-level overview: structure, conventions, how to add things,
requirements. One dense paragraph per topic, no fluff.
.SH FILE HEADERS
.PP
Every file starts with a path comment and a header block:
.nf
.IP
\-\- lua/modules/compile.lua

\-\- Native, Emacs-like \(ga:Compile\(ga that runs a build command
\-\- asynchronously and streams its output into a \(ga*compilation*\(ga
\-\- buffer in a bottom split. When the command fails, the output
\-\- is parsed into the quickfix list.
\-\-
\-\- [behavior details, state model, decisions]
\-\-
\-\- The \(gago\(ga CLI comes from the distribution:
\-\-
\-\- $ sudo pacman \-S go
\-\-
\-\- See: lua/config/autocmds.lua
\-\- See: :help quickfix
.fi
.PP
The rules of the header:
.IP \(bu 2
Line 1 is the file's own path: \fB\-\- lua/<path>.lua\fR, or
\fB\-\- after/ftplugin/python.lua\fR for ftplugins.
.IP \(bu 2
One blank line, then the header block.
.IP \(bu 2
The first paragraph answers "what is this and why does it exist".
Behavior details follow as more paragraphs, one concern per
paragraph.
.IP \(bu 2
Decisions are stated with their reasons: "on purpose", "because",
"so that". A reader should be able to distinguish a choice from an
accident.
.IP \(bu 2
Facts that live in another file are not restated; they are
referenced (see
.B CROSS-REFERENCES
below).
.IP \(bu 2
External tool requirements are documented in the header of the file
that uses them, as shell lines (\fB$ sudo pacman \-S ...\fR) or Mason
commands (\fB:MasonInstall ...\fR). Requirements are never collected
in a distant requirements file only; the header is where they are
found.
.IP \(bu 2
If a module exposes setup() and owns its state, the header says so,
and any init-order constraint (like "must be called before
pack.lua") is stated explicitly.
.SH CROSS-REFERENCES
.PP
Any pointer to related material is a \fBSee:\fR line, grouped at the
bottom of the header (or after the relevant paragraph when the
reference is local to one concern):
.nf
.IP
\-\- See: lua/config/pack.lua        a file, from the repo root
\-\- See: :help lsp                  a help tag
\-\- See: man:rg                     a man page
\-\- See: https://github.com/...     an external source
.fi
.PP
Conventions:
.IP \(bu 2
File paths are relative to the repo root and are written in full
(\fIlua/lib/buffers.lua\fR), never as bare file names.
.IP \(bu 2
References are symmetric when it makes sense: if A's header says
"See: B", B's header usually says "See: A". The goal is that a
reader can traverse the whole feature from any of its files.
.IP \(bu 2
Inline \fBSee:\fR comments in the body mark the spot where a
dependency matters, e.g. above a sessionoptions line that must match
\fImodules/sessions.lua\fR.
.IP \(bu 2
Trivial, adjacent references are omitted. Not everything is linked;
only what a reader would otherwise miss.
.SH FORMATTING AND STYLE
.IP \(bu 2
Language: English, present tense, third person. "The module saves
the session", not "we save".
.IP \(bu 2
Code identifiers (option, function, Command) are quoted in
backticks.
.IP \(bu 2
Comments wrap around column 78, aligned with the file body.
.IP \(bu 2
The buffer-local \fBopt_local\fR, global \fBvim.opt\fR and window
\fBvim.wo\fR scopes are named when the distinction matters.
.IP \(bu 2
TODO comments state the missing thing and its context, not a mood.
.IP \(bu 2
Deprecation: modules that fall out of use move to
\fIlua/archived/\fR, outside \fIlua/\fR and off the runtimepath, with
their header intact.
.SH THE TWO FORMATS OF THE PAGES
.PP
Each page exists twice, and the two copies say the same thing:
.TP
.I doc/pages/<name>.txt
the roff source, written with the man(7) macros. \fBman\fR reflows it
to the available width of the terminal. This is the canonical copy.
.TP
.I doc/<name>.txt
a plain-text mirror of the style, not of the rendering: the same
sections and lists, but paragraphs written at full width, left to
the editor's wrap, with no macros, no bold and no page header or
footer. It is what gets updated first when a page changes.
.PP
\fIdoc/reading.txt\fR explains how to read both formats and lists the
commands. The roff pages are rendered like this:
.nf
.IP
man \-l doc/pages/kickstart.txt
:read !man \-l doc/pages/kickstart.txt
.fi
.PP
Their structure:
.TP
.B NAME
one line: page name \- short description
.TP
.B SYNOPSIS
how to read the page
.TP
.B DESCRIPTION
what the subject is
.TP
.B ...
topic sections, in reading order
.TP
.B FILES
related files
.TP
.B SEE ALSO
other pages and help tags
.PP
Rules for these pages:
.IP \(bu 2
The roff source is written in man(7): \fB.TH\fR, \fB.SH\fR,
\fB.PP\fR, \fB.TP\fR, \fB.IP \(bu\fR, \fB.B\fR/\fB.I\fR. Paragraph
text is filled by groff, so no hard wrapping; preformatted blocks
(code, trees, shell commands) are wrapped in \fB.nf\fR/\fB.fi\fR.
The plain-text mirror follows the same section order, writes each
paragraph as a single full-width line for the editor to wrap, and
marks emphasis only with quotes.
.IP \(bu 2
No keymaps. They change too often; a stale keymap list is worse than
none. Pages describe features, commands, files and behavior, and
point to the keymap files for the rest.
.IP \(bu 2
Commands are documented with their arguments, even when a keymap
also triggers them: commands are stable, keymaps are not.
.IP \(bu 2
Dates or version numbers in headers rot; the footer date and the
git history cover that.
.SH KEYMAPS
.PP
Keymaps are the deliberate exception to "document everything":
.IP \(bu 2
They are never listed in \fIdoc/\fR or in the README.
.IP \(bu 2
The keymap files under \fIlua/config/keymaps/\fR have minimal headers
(a sentence about the group's scope) and rely on \fBvim.keymap.set\fR
desc fields, which surface in the shortlist and \fB:map\fR, as the
documentation.
.IP \(bu 2
A keymap that only makes sense inside one plugin lives in that
plugin's file; all others live in the matching theme file under
\fIlua/config/keymaps/\fR.
.IP \(bu 2
When a feature page (e.g.
.B COMPILATION
in \fIkickstart.txt\fR) needs a trigger documented, the user command
is documented instead.
.SH KEEPING DOCS CURRENT
.PP
Documentation is part of the change:
.IP \(bu 2
A behavior change updates the header of the file that owns it, in
the same commit. A decision added to code without its reason in the
header is half a change.
.IP \(bu 2
When moving a feature between layers, its \fBSee:\fR web moves with
it; dead references are bugs.
.IP \(bu 2
When adding a new module kind or a new convention, document it here,
in this page.
.IP \(bu 2
The README is updated only for structural or requirement changes,
not for every small edit.
.SS Review checklist for a doc-affecting patch
.IP 1.
Does the file header still describe what the file does?
.IP 2.
Do new decisions carry their reasons?
.IP 3.
Are new external tools documented with their install command in the
header?
.IP 4.
Are \fBSee:\fR references added, and none left dangling?
.IP 5.
Do the doc/ pages contradict the code anywhere?
