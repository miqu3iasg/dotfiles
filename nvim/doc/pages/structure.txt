.TH STRUCTURE 7 "2026" "nvim config"
.SH NAME
structure \- the folder structure of this Neovim configuration
.SH SYNOPSIS
.nf
man \-l doc/pages/structure.txt
:read !man \-l doc/pages/structure.txt
.fi
.SH DESCRIPTION
.PP
The tree is organized so that every kind of knowledge has exactly one
home: editor behavior at startup, plugin adapters, whole features,
shared helpers, language servers, snippets and filetype options each
get a folder of their own. A new contributor should be able to guess
where a change goes from the change alone, without reading the code
first.
.SH THE TREE
.nf
nvim/
|\- init.lua               entry point; fixes the load order, nothing
|                         else
|\- colors/                custom colorschemes, one file per scheme
|\- after/
|  |\- ftplugin/           buffer-local options per filetype,
|  |                      applied after the runtime ftplugins
|  |- queries/            Tree-sitter query overrides
|\- lua/
|  |\- config/             editor behavior loaded at startup
|  |\- plugins/            one adapter file per plugin suite
|  |\- modules/            whole features written for this config
|  |\- lib/                shared utilities and domain logic
|  |\- language/           the language server stack
|  |\- snippets/           LuaSnip snippets, one file per filetype
|  |- archived/           deprecated modules, off the runtimepath
|\- pandoc/                Pandoc pipeline: defaults, metadata,
|                         profiles and Lua filters
|\- resources/             example configuration for external tools
|\- spell/                 custom spell files
|\- doc/                   man pages (this folder)
|\- nvim-pack-lock.json    revision lock file written by vim.pack
\- LICENSE
.fi
.SH TOP-LEVEL FOLDERS
.SS colors/
.PP
Colorschemes are runtimepath-loaded by \fBvim.cmd.colorscheme\fR, so
they live in the conventional \fIcolors/\fR folder, outside \fIlua/\fR.
One file per scheme; the scheme name is the file name.
.SS after/
.PP
The \fIafter/\fR directory is loaded after everything else in the
runtimepath, which is exactly what filetype overrides need:
\fIafter/ftplugin/<ft>.lua\fR runs after Neovim's own ftplugin for
the filetype, so its options win. That is why every filetype option
lives here and not in a custom layer. \fIafter/queries/\fR overrides
Tree-sitter queries the same way (Markdown textobjects).
.SS pandoc/
.PP
The export pipeline is data, not code: \fIdefaults.yaml\fR (the
writer pipeline), \fImetadata.yaml\fR (default layout and language),
\fIprofiles/\fR (per-document styles, such as \fIabnt.yaml\fR) and
\fIfilters/\fR (wikilinks, metadata blocks, citations). The Lua
module \fIlua/modules/pandoc.lua\fR orchestrates these files; it
holds no document logic itself.
.SS resources/
.PP
Example configuration files for external tools that the config does
not own (\fIclang-format.example.yaml\fR). Kept out of \fIlua/\fR
because they are reference material, never loaded.
.SS doc/
.PP
Man pages describing the config, in two copies: the roff sources in
\fIdoc/pages/\fR and the plain-text mirrors in \fIdoc/\fR, written at
full width for the editor to wrap.
\fIdoc/reading.txt\fR explains how to read them; the standard itself
is \fIdocumentation.txt\fR.
.SS spell/
.PP
Custom spell dictionaries, loaded by Neovim's spelling machinery
directly.
.SH THE LUA LAYERS
.PP
Everything under \fIlua/\fR is split into layers by what a file is,
and the split is the contract:
.SS config/ \- behavior loaded at startup
.PP
\fIoptions.lua\fR (global options), \fIautocmds.lua\fR (global
autocmds), \fIcommands.lua\fR (user commands), \fIpack.lua\fR
(vim.pack declarations and build hooks), and \fIkeymaps/\fR (keymaps
split by theme, one file per group, with its own init.lua that sets
the leaders). Files here run once, in the order fixed by
\fIinit.lua\fR, and are not required by anything else.
.SS plugins/ \- adapters for third-party plugins
.PP
One file per plugin suite, never more. The file owns the plugin's
setup and any keymap that only makes sense inside it. A plugin that
should load lazily declares that itself, at the bottom of its own
file, through lib/lazy.lua. \fIinit.lua\fR in this folder is the
ordered load list.
.SS modules/ \- whole features written for this config
.PP
Self-contained components such as the statusline, per-directory
sessions, the scratch buffer, the compile runner and the notes
workflow. Each exposes setup() when it must register commands,
autocmds or keymaps, and owns its own state, reached only through
its API. See \fIdoc/pages/modules.txt\fR.
.SS lib/ \- shared utilities and domain logic
.PP
Everything that exists to be required by other modules: the buffer
helpers, the big-file detector, the lazy loader, the autoformat
state, the export path logic and so on. The criterion is binary:
something that exposes commands, autocmds or keymaps goes in
\fImodules/\fR; anything else goes in \fIlib/\fR. See
\fIdoc/pages/lib.txt\fR.
.SS language/ \- the language server stack
.PP
One module per server under \fIservers/\fR (config table plus an
optional on_attach hook), the shared setup in \fIinit.lua\fR, the
module contract in \fItypes.lua\fR and the external linters in
\fIlint.lua\fR. It slots into the plugins load list as a full
module, because it must load between completions and fzf.
.SS snippets/ \- LuaSnip snippets
.PP
One file per filetype, loaded lazily; shared and
filetype-adaptive helpers in \fIcommon.lua\fR.
.SS archived/ \- deprecated, not deleted
.PP
Modules kept around for possible future use. They sit outside
\fIlua/\fR and off the runtimepath on purpose: Neovim cannot reach
them, but git history and the headers stay intact.
.SH LAYER RULES
.PP
A layer may only require the layers below it, in this order:
.nf
.IP
init.lua > config > plugins > modules > lib
.fi
.PP
Nothing in \fIlib/\fR requires upwards, ever. This is what makes
removal cheap: deleting an eager plugin means deleting its file in
\fIplugins/\fR, its entry in \fIconfig/pack.lua\fR and its entry in
\fIplugins/init.lua\fR; a lazy plugin is fully self-declared in its
adapter and vanishes with that file alone.
.PP
The rule also decides disputes. When a change wants to break it \- a
lib helper that wants to create a command, a module that wants to be
required by lib \- the fix is structural, not a workaround: move the
domain logic to \fIlib/\fR and let the caller pass state in, or
merge the two files into the lower layer.
.SH FINDING THINGS
.PP
Where does X live?
.TP
An option
\fIconfig/options.lua\fR, or \fIafter/ftplugin/<ft>.lua\fR when per
filetype
.TP
A global autocmd
\fIconfig/autocmds.lua\fR
.TP
A user command
\fIconfig/commands.lua\fR, or the module that owns it
.TP
A keymap
the matching file in \fIconfig/keymaps/\fR, or the plugin's adapter
when plugin-specific
.TP
A plugin's setup
its adapter in \fIplugins/\fR
.TP
A whole feature
the module in \fImodules/\fR named after it
.TP
A helper other files use
\fIlib/\fR
.TP
A language server
\fIlanguage/servers/<server>.lua\fR
.TP
An external linter
\fIlanguage/lint.lua\fR
.TP
A snippet
\fIsnippets/<ft>.lua\fR
.TP
Filetype options
\fIafter/ftplugin/<ft>.lua\fR
.TP
Export path logic
\fIlib/exports.lua\fR
